# 下载并发与断点续传

0.2.1-dev 使用现有前台 dataSync 服务调度任务，同一时刻处理一个 APK，避免多任务同时占满电视网络与存储。APK 大于等于 4 MiB 时先用 `Range: bytes=0-0` 检查分段支持，支持时开启最多 4 个连接；小文件使用单连接。服务器忽略 Range 时自动回退为单连接完整下载。

## 进度与恢复

- 单连接写入 `<taskId>.part`，续传时请求尚未收到的字节。
- 分段分别写入 `<taskId>.part.chunks/0.chunk` 至 `3.chunk`，每段按实际文件长度续传。应用进程退出、网络断开后仍保留这些文件；再次进入下载中心选择“继续下载”（尚无已报告进度时显示“重试”）即可恢复。
- `identity.properties` 记录 URL、预期大小、SHA-256、下载模式和服务端 validator。强 ETag 优先，缺失时使用 Last-Modified，并发送 If-Range。资源身份或分段 validator 变化时丢弃旧进度。
- 服务器将续传请求返回为 200 时，从零写入，绝不把完整文件追加到旧内容。服务器最初接受探测、随后忽略分段时，也会停止分段并回退。
- 用户主动取消会停止网络请求并清理临时文件；网络失败、系统中断则保留进度。失败重试由用户在下载中心触发，不会无限自动重试。
- 清理缓存会清理非活动任务的临时文件；此后重试从零开始。

## 合并与安装

严格检查每个响应的 Content-Range、Content-Length、内容编码和实际字节数。分段合并后重新核对整包大小与 SHA-256；校验失败删除临时内容，不生成可安装 APK。允许的 GitHub 官方发布来源、重定向白名单、发布证书、包名、ABI / SDK 检查沿用现有流程。

实现依据：[HTTP Range、Content-Range 与 If-Range 语义（RFC 9110）](https://www.rfc-editor.org/rfc/rfc9110.html#section-14)。没有 Range 支持时，客户端无法让服务器真正断点续传，因此采用完整下载回退。

## 验证范围

`ResumableDownloadTest` 的 13 项测试通过本机 MockWebServer 验证 4 个请求真实重叠、单连接/分段的独立偏移恢复、真实 socket 断线、ETag 改变、资源身份变化、Range 忽略、范围错误、损坏分段和主动取消。原有下载 SHA-256 / 来源测试继续运行。

尚未测量实体电视下载吞吐，未宣称四连接必然提速；GitHub CDN 与网络环境可能限制速度。真实第三方 APK 安装流程此前已验证，本轮未重新联网安装第三方应用。
